# 原 Android eMMC 备份经验

本板已在 TF Debian 下只读提取原 Android 的普通 eMMC 区，并保存到私有服务器。
下面记录本次有效的方法和验证标准，**尚不是通用采集脚本或经过刷回验证的恢复教程**。

## 备份范围

| 区域 | 参考样本原始大小 | 用途 |
| --- | --- | --- |
| eMMC user area | 15,655,239,680 字节 | 含分区表、Android 系统和用户数据 |
| boot0 | 4MiB | eMMC 硬件启动区 |
| boot1 | 4MiB | eMMC 硬件启动区 |

整盘 gzip 是原始块镜像的压缩文件，**不是 Rockchip `update.img`**。
RPMB 认证区、SoC 熔丝及其他受保护硬件状态不包含在普通块镜像中；
这份备份不承诺跨设备克隆，也不等于恢复出厂设置。

备份可能含账号、用户数据和设备身份，只能保存到受限私有存储。
公开仓库保留方法，镜像、CID/CSD/EXT_CSD、设备专属清单和原始日志不上传。

## 先得到稳定的只读源

TF DTS 禁用 eMMC。备份从 TF 系统进行，通过**临时 RAM 设备树**启用 eMMC，保留默认启动文件，
按原厂配置使用 8 位总线、VCC 3.3V、VQMMC 1.8V，并限制为 50MHz。
这些电气参数需对照目标板确认，不能靠容量或接口外形推定。

在受控临时启动中，通过 udev 对类型为 `MMC` 的主块设备设置只读；boot0/boot1 保持只读。
读取前同时确认：源设备是 eMMC、系统根位于 SD、源各区均未挂载且 RO=1，Android 没有运行。
不能把“当前是 mmcblk1”作为永久身份依据。
启用额外控制器可能改变编号，本次使用按唯一 TF 标签寻找根分区的既有 initramfs 维护环境。
启用控制器可参考 [eMMC 设备树](../board/rk3288-emb3533-emmc.dts)，但设备树本身不会把块设备设为只读。
只读策略和维护 initramfs 需单独准备，仓库不提供自动采集环境。

## 有效的数据路径

```text
eMMC 只读源
  → 单次连续读取，同时计算原始 SHA-256
  → pigz -1 -p2，落到 TF /var/tmp 的受限暂存目录
  → 完成后原子改名，计算压缩文件 SHA-256
  → Mac 用 scp -3 中转到私有服务器，不在 Mac 落完整镜像
  → 服务器完整解压计数、校验原始摘要与压缩摘要
  → 校验通过后将 .partial 改为正式文件，生成清单
```

这是效率与可靠性之间的实际选择。TF 暂存需要足够空间；不要放到可能为 tmpfs 的 `/tmp`。
参考样本主区单次读取、摘要与压缩约 **12 分 22 秒**，加两个启动区后压缩总量约 **929MB**，
原始总量约 **15.66GB**。这是本次数据内容下的结果，已有大量数据的设备压缩率会不同。
主源不必为了服务器校验再读一次：服务器解压后的摘要与源首次读取时的原始摘要比较即可。

`scp -3` 使用 Mac 的两端 SSH 认证中转已有文件，优先保留成熟传输协议；
源端仍要准备完整压缩暂存文件。服务器目标文件在完成校验前保留 `.partial` 名称。
Windows 目标用 SFTP 路径并先做小文件试传，避免把不同 shell 的路径规则混用。

## 哪些尝试没有推广

- ARM32 上硬编码 64 位平台的 `BLKGETSIZE64` ioctl 编号会返回 EINVAL；用 `blockdev --getsize64` 查询实际大小。
- Windows PowerShell 5.1 的文本管道不能传递磁盘二进制流。
  本次自制接收器虽通过小样，持续双向流没有稳定完成，因此改用 TF 暂存加 SFTP。
- 复杂 PowerShell 经 stdin 发送有执行时机差异，服务器校验更适合上传脚本后 `-File`，
  或明确使用 UTF-16LE `EncodedCommand`；清单使用明确的 UTF-8 编码。

不因某次连接断开而立即重传：先查目标文件、长度和接收任务状态。
已知未开始传输的认证前连接失败，可以单独处理；未知状态保留现场和回执。

## 完成标准与收尾

每个区域分别记录名称、原始长度、原始 SHA-256、压缩长度、压缩 SHA-256。
服务端须完整读取并解压每个 gzip，核对解压字节数与原始摘要；只通过 gzip 头检查或文件存在不算完成。
随后核对清单读回、文件落盘和目录权限。本次 Windows 目录关闭权限继承，仅保留必要管理主体。

全部镜像校验后，再删除本次 TF 暂存、临时规则和 RAM DTB，重启回 TF 配置，
确认 eMMC 再次不可见、TF 根正确、SSH/网络恢复、没有残留 kexec 或诊断任务。

本次三个镜像已经通过源端与服务器双摘要、完整解压长度验证。
**尚未向 eMMC 刷回并验证 Android 启动**；恢复演练需另行准备完整恢复入口，并明确授权写回。
